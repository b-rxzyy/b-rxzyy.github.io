## Overview

TriKDF Enterprise is a custom cryptography challenge based on triangle
side lengths, trigonometric calculations, state rotations, and AES-GCM.

The key weakness is that the application checks only that each side is
within the allowed numerical range. It does **not** verify that the
three values actually form a valid triangle.

Using the invalid triangle:

``` text
A = 1
B = 1
C = 3
```

causes the cosine-rule calculations to produce `NaN`. Those values
propagate through the custom state-mixing algorithm, making the final
key derivation predictable without knowing the remote `MASTER_SECRET`.

# Source Analysis

## Side-Length Validation

The application allows side lengths between `1` and `65535`.

The individual range checks are not enough. A valid triangle must also
satisfy:

``` text
a + b > c
a + c > b
b + c > a
```

Those conditions are missing.

Therefore:

``` text
1, 1, 3
```

is accepted even though:

``` text
1 + 1 < 3
```

------------------------------------------------------------------------

## Cosine Rule

The angles are calculated with:

``` python
alpha = np.arccos(
    (b * b + c * c - a * a) / (2.0 * b * c)
)

beta = np.arccos(
    (a * a + c * c - b * b) / (2.0 * a * c)
)

gamma = np.arccos(
    (a * a + b * b - c * c) / (2.0 * a * b)
)
```

`np.arccos()` expects a value in `[-1, 1]`.

For `(1, 1, 3)`:

``` text
alpha = arccos((1² + 3² - 1²) / (2 × 1 × 3))
      = arccos(9 / 6)
      = arccos(1.5)
      = NaN
```

The invalid operation is ignored using NumPy's error-state handling, so
execution continues.

The other angle calculations are also invalid and produce `NaN`.

------------------------------------------------------------------------

# NaN Propagation

The angles are used by the rotation function:

``` python
cosine = np.cos(angle)
sine = np.sin(angle)

x = state[first]
y = state[second]

state[first] = cosine * x - sine * y
state[second] = sine * x + cosine * y
```

For a `NaN` angle:

``` text
sin(NaN) = NaN
cos(NaN) = NaN
```

Therefore the state becomes contaminated with `NaN` values.

The challenge repeatedly rotates and permutes the state. The `NaN`
values consequently propagate through the state until the final state
becomes predictable for the malicious input.

------------------------------------------------------------------------

# Key Derivation

The initial state is derived from the secret using SHA-512.

The final AES key is then generated with SHA-256 from:

``` text
"TriKDF-v1 AES-256"
+
serialized triangle
+
serialized final state
```

The important observation is that the invalid triangle causes the state
to lose its useful dependence on the secret.

For:

``` text
A = 1
B = 1
C = 3
```

the derived AES-256 key is:

``` text
8b298685fad79c96b0495bdf357696001621f8feeebaebc6e071ba5919386d9b
```

# Decryption

![tri](/assets/ctf2.png)

The ciphertext can be decrypted with AES-GCM:

``` python
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

key = bytes.fromhex(
    "8b298685fad79c96b0495bdf357696001621f8feeebaebc6e071ba5919386d9b"
)

nonce = bytes.fromhex(
    "e81864b9ae6095003f386365"

)

print(
    AESGCM(key)

```

# Conclusion

TriKDF Enterprise looks complicated because it combines custom
mathematics with cryptographic primitives, but the exploit is ultimately
straightforward.

The critical input is:

``` text
1
1
3
```

This creates an invalid triangle, causes the cosine-rule calculations to
return `NaN`, and lets those values propagate through the custom KDF.

The resulting AES key can then be reproduced and used to decrypt the
remote ciphertext.

The final flag is:

``` text
brunner{n0-c0mpl1c4t_Tr14ngl3s}
```

The challenge is a good example of how seemingly harmless numerical edge
cases and missing input validation can completely undermine a
cryptographic construction.
