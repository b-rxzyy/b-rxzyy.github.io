# Web API Architecture 

The goal is to understand **what happens to an API request from the moment you send it until the response comes back**, and then connect that architecture to **REST, GraphQL, authentication, authorization, business logic, databases, and API security testing**. 

---

# 1. The Big Picture

A Web API is essentially a **communication layer between a client and backend systems**.

The client sends an HTTP/HTTPS request → the API processes it → the API may communicate with databases or other services → the API sends an HTTP response back.

```text
                         ┌──────────────────────────┐
                         │      CLIENT / YOU        │
                         │ Browser / Mobile / App   │
                         └────────────┬─────────────┘
                                      │
                                      │ HTTPS Request
                                      │
                                      │ Authorization:
                                      │ Bearer <JWT>
                                      ▼
                         ┌──────────────────────────┐
                         │    API GATEWAY / WAF     │
                         │                          │
                         │ • Routing                │
                         │ • Rate Limiting          │
                         │ • Request Filtering      │
                         │ • TLS / HTTPS            │
                         └────────────┬─────────────┘
                                      │
                                      ▼
                         ┌──────────────────────────┐
                         │       API SERVER         │
                         │                          │
                         │ REST / GraphQL           │
                         │        │                 │
                         │        ▼                 │
                         │   AUTHENTICATION         │
                         │        │                 │
                         │   ┌────┴─────────────┐   │
                         │   │                  │   │
                         │  JWT            OAuth 2.0│
                         │   │                  │   │
                         │   └────┬─────────────┘   │
                         │        ▼                 │
                         │   AUTHORIZATION          │
                         │        │                 │
                         │ "What can you access?"   │
                         │        ▼                 │
                         │   Input Validation       │
                         │        │                 │
                         │        ▼                 │
                         │   Business Logic         │
                         └────────────┬─────────────┘
                                      │
                                      │ Database Query
                                      ▼
                         ┌──────────────────────────┐
                         │        DATABASE          │
                         │                          │
                         │ Users                    │
                         │ Orders                   │
                         │ Payments                 │
                         │ Profiles                 │
                         │ Settings                 │
                         └────────────┬─────────────┘
                                      │
                                      │ Data
                                      ▼
                         ┌──────────────────────────┐
                         │       API SERVER         │
                         └────────────┬─────────────┘
                                      │
                                      │ HTTP Response
                                      │ JSON
                                      ▼
                         ┌──────────────────────────┐
                         │      CLIENT / YOU        │
                         └──────────────────────────┘
```


The simplified model is:

```text
CLIENT
  ↓
HTTPS
  ↓
API GATEWAY / WAF
  ↓
REST or GraphQL
  ↓
AUTHENTICATION
  ↓
AUTHORIZATION
  ↓
BUSINESS LOGIC
  ↓
DATABASE
  ↓
API SERVER
  ↓
HTTP RESPONSE
  ↓
CLIENT
```

This overall architecture is also reflected in the source material.

# 2. Client Where the Request Comes From

The **client** is whatever application is communicating with the API.

Examples:

```text
Browser
Mobile App
Desktop Application
JavaScript Frontend
IoT Device
```

For example, imagine you are logged in as User 1 and open your profile.

Your browser could send:

```http
GET /api/users/1 HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Accept: application/json
```

In simple terms:

> "API, give me the information for User 1."

The client normally **does not communicate directly with the database**.

Instead:

```text
Client
   ↓
API Server
   ↓
Database
```

This allows the API to control what data the client can access.

# 3. HTTP / HTTPS

The client communicates with the API using **HTTP or HTTPS**.

```text
HTTP
 ↓
Communication protocol

HTTPS
 ↓
HTTP + TLS encryption
```

Modern APIs normally use HTTPS because it protects HTTP traffic using TLS.

A request can contain:

```text
HTTP Method
URL / Endpoint
Headers
Cookies
Parameters
Request Body
Authentication Token
```

Example:

```http
GET /api/users/1 HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Accept: application/json
```

Think of an HTTP request as a package containing:

```text
┌────────────────────────────┐
│ HTTP REQUEST               │
├────────────────────────────┤
│ Method                     │
│ Endpoint                   │
│ Headers                    │
│ Authentication             │
│ Parameters                 │
│ Body                       │
└────────────────────────────┘
```

---

# 4. API Endpoint

An **endpoint** is a URL through which you interact with a particular API resource or operation.

Examples:

```text
/api/users
/api/users/123
/api/products
/api/orders
/api/payments
```

For example:

```http
GET /api/users/
```

could mean:

> Give me a list of users.

While:

```http
GET /api/users/123
```

could mean:

> Give me information about User 123.

A useful distinction is:

### Collection

```text
/api/users
```

Means:

> A collection of users.

### Individual resource

```text
/api/users/123
```

Means:

> User 123.

### Subcollection

```text
/api/users/123/orders
```

Means:

> Orders belonging to User 123.

---

# 5. HTTP Methods

The HTTP method tells the API what type of operation you're requesting.

| Method   | Meaning         | Typical Use                         |
| -------- | --------------- | ----------------------------------- |
| `GET`    | Read            | Retrieve data                       |
| `POST`   | Create / Action | Create data or perform an operation |
| `PUT`    | Update          | Replace/update a resource           |
| `PATCH`  | Partial Update  | Modify part of a resource           |
| `DELETE` | Delete          | Remove a resource                   |

### Example

```http
GET /users/123
```

Read User 123.

```http
POST /users
```

Create a user.

```http
PUT /users/123
```

Update User 123.

```http
PATCH /users/123
```

Partially update User 123.

```http
DELETE /users/123
```

Delete User 123.

# 6. CRUD

CRUD is one of the easiest concepts to remember.

```text
C → Create
R → Read
U → Update
D → Delete
```

Typical mapping:

```text
POST    → CREATE
GET     → READ
PUT     → UPDATE
DELETE  → DELETE
```

Example:

```http
POST /users
```

```text
Create User
```

```http
GET /users/1
```

```text
Read User 1
```

```http
PUT /users/1
```

```text
Update User 1
```

```http
DELETE /users/1
```

```text
Delete User 1
```

However, APIs can also have actions that don't fit traditional CRUD:

```http
POST /users/1/activate
POST /orders/10/refund
POST /password/reset
```

So don't assume that API behavior is limited to CRUD.

# 7. API Gateway / WAF

After leaving the client, a request may reach an **API Gateway** or **WAF**.

Think of this as the:

> **Front door / security checkpoint of the API.**

```text
CLIENT
   ↓
API GATEWAY / WAF
   ↓
API SERVER
```

The gateway can perform several functions.

### 7.1 Routing

It decides where the request should go.

```text
/api/users
      ↓
User Service

/api/orders
      ↓
Order Service

/api/payments
      ↓
Payment Service
```

### 7.2 Rate Limiting

Controls how frequently a client can make requests.

```text
Client
  ↓
Request
  ↓
Rate Limiter
  ↓
Too many requests?
  ↓
429 Too Many Requests
```

### 7.3 Request Filtering

The gateway/WAF can inspect requests and block unwanted or potentially malicious traffic.

### 7.4 TLS/HTTPS

The gateway may also handle TLS termination or HTTPS-related processing.

### 7.5 Load Balancing

Traffic can be distributed between multiple backend servers.

```text
             ┌── API Server 1
             │
Client → Gateway
             │
             ├── API Server 2
             │
             └── API Server 3
```

The API Gateway therefore acts as an important **entry point into the backend infrastructure**. 

---

# 8. WAF vs API Gateway

They can exist together, but they are not exactly the same thing.

### WAF

Primarily focused on:

```text
Filtering
Blocking malicious traffic
Web attack protection
Request inspection
```

### API Gateway

Primarily focused on:

```text
Routing
Rate limiting
API management
Authentication integration
Traffic control
Load balancing
```

You might see:

```text
Client
  ↓
WAF
  ↓
API Gateway
  ↓
API Server
```

Or a platform may combine some of these responsibilities.

# 9. API Server

The **API server** is where the backend application processes the request.

For example:

```http
GET /api/users/1
```

reaches the API server.

The server might think:

```text
Who is making this request?
        ↓
Is their credential valid?
        ↓
What are they allowed to access?
        ↓
Is this request valid?
        ↓
What does the business logic require?
        ↓
What database data is needed?
        ↓
Return the appropriate response
```

The API server can handle:

```text
Authentication
Authorization
Input Validation
Business Logic
Database Queries
Response Generation
```

# 10. REST and GraphQL

The API server may expose different API styles.

The two important ones from your material are:

```text
REST
GraphQL
```

They both commonly use HTTP, but they work differently.

# 11. REST API

REST stands for:

> **Representational State Transfer**

REST is **not a protocol**.

It is a set of architectural guidelines for building APIs over HTTP.

REST commonly works with resources:

```text
/users
/products
/orders
/payments
```

Example:

```http
GET /api/users/1
```

Meaning:

> Give me User 1.

REST commonly uses HTTP methods:

```text
GET     → Read
POST    → Create / Action
PUT     → Update
PATCH   → Partial Update
DELETE  → Delete
```

---

# 12. REST Constraints

REST has six main architectural constraints.

## 12.1 Uniform Interface

Clients interact with resources through a consistent interface.

```text
Browser
Mobile App
Desktop App
IoT Device
      ↓
     REST API
```

---

## 12.2 Client-Server

The client and server have separate responsibilities.

```text
CLIENT
  ↓
Requests data/actions
  ↓
SERVER
  ↓
Provides data/actions
```

The client handles the user interface.

The server handles application logic and data.

---

## 12.3 Stateless

This is extremely important.

> **Each request should contain the information necessary for the server to process it.**

Example:

```http
GET /api/users/1
Authorization: Bearer <token>
```

Then:

```http
GET /api/users/1/orders
Authorization: Bearer <token>
```

The server processes each request independently.

Easy way to remember:

```text
Every request
      ↓
Contains what the server needs
```

The source material specifically emphasizes that REST requests should carry the information required to understand them. 

---

# 13. Cacheable

REST responses can be cached.

Instead of repeatedly asking the server for the same information:

```text
Client
  ↓
Server
  ↓
Product 10
```

a cache can store the response:

```text
Client
  ↓
Cache
  ↓
Product 10
```

This can reduce:

```text
Response time
Server processing
Database queries
Network traffic
```

Caching behavior can be controlled using HTTP headers such as:

```http
Cache-Control: max-age=3600
```

---

# 14. Layered System

The client doesn't need to know how the backend is internally constructed.

For example:

```text
Client
  ↓
API Gateway
  ↓
API Server
  ↓
Microservice
  ↓
Database
```

The client simply sees:

```text
API
```

It doesn't need to know whether the backend contains:

```text
Load Balancers
Multiple Servers
Caches
Microservices
Databases
API Gateways
```

This is the **layered system** concept. 

---

# 15. Code on Demand

This REST constraint is optional.

The server can optionally send executable code to the client.

For example:

```text
Server
  ↓
JavaScript
  ↓
Browser
  ↓
Execute JavaScript
```

# 17. HTTP Response Status Codes

The API communicates the result using HTTP status codes.

| Code  | Meaning                        |
| ----- | ------------------------------ |
| `200` | Success                        |
| `201` | Created                        |
| `400` | Bad Request                    |
| `401` | Authentication required/failed |
| `403` | Forbidden                      |
| `404` | Not Found                      |
| `429` | Too Many Requests              |
| `500` | Server Error                   |

Important security distinction:

```text
401
 ↓
Authentication problem

403
 ↓
You are authenticated, but access is forbidden
```

The source specifically highlights `401`, `403`, `404`, and `429` as useful codes to understand during API security testing.

# 18. REST Headers

Headers provide additional information about a request or response.

Important headers include:

```text

```

## Authorization

Example:

```http

```

---

## Content-Type

Tells the server what type of data you are sending.


Means:

Common types:

```text

application/x-www-form-urlencoded
```

Tells the server what response format the client wants.


Means:

> I want JSON back.

Easy trick:

```text

      ↓

      ↓
"What do I want back?"
```

# 20. GraphQL

GraphQL is a **query language and API approach** where the client can specify the data it wants.

The major difference is:

```text
REST
 ↓
Server generally determines response structure

GraphQL
 ↓
Client specifies requested fields
```

# 21. REST vs GraphQL

### REST

```http
GET /api/users/1
```

The server determines the response.

Example:

```json
{
  "id": 1,
  "username": "user1",
  "email": "user1@example.com",
  "phone": "123456789",
  "address": "..."
}
```

Maybe you only wanted:

```text
username
email
```

but the endpoint returns additional fields.

### GraphQL

You can request specific fields:

```graphql
query {
  users {
    username
    id
    email
  }
}
```

The server returns the requested fields.

Easy mental model:

```text
REST
 ↓
"Give me this resource."

GraphQL
 ↓
"Give me these specific fields."
```

The provided material makes exactly this distinction.

# 26. Authentication

Now we reach one of the most important parts of the architecture.

Authentication answers:

> **WHO ARE YOU?**

Example:

```text
Client
   ↓
Credentials / Token
   ↓
API
   ↓
Verify identity
   ↓
User 1
```

For example:

```http
Authorization: Bearer <token>
```

The server checks whether the credential is valid.

If authentication fails, the API may return:

```http
401 Unauthorized
```

The fundamental distinction is:

```text
Authentication
      ↓
"Who are you?"

Authorization
      ↓
"What are you allowed to access?"
```



---

# 27. Authorization

After authentication, the API needs to determine what the user can actually do.

Suppose:

```text
User = user1
```

The server might determine:

```text
View own profile        ✓
View own orders         ✓
Delete another user     ✗
Access admin panel      ✗
```

So:

```text
Authentication
      ↓
Identify User 1
      ↓
Authorization
      ↓
Determine User 1's permissions
```

This is extremely important for API security.

# 29. Basic Authentication

Basic Authentication sends:

```text
Username + Password
```

Example:

```http
Authorization: Basic <credentials>
```

Conceptually:

```text
username:password
       ↓
   Base64 encoding
       ↓
Authorization header
```

### Very important

```text
Base64 ≠ Encryption
```

Base64 can easily be decoded.

Therefore Basic Authentication should be protected using HTTPS/TLS.

# 30. API Keys

An API key is a unique value issued by the API provider.

Basic flow:

```text
Register
   ↓
Receive API Key
   ↓
Send API Key
   ↓
API checks key
   ↓
Allow / Deny
```

Example:

```http
API-Key: YOUR_KEY
```

It may also appear as:

```http
GET /api/users?apikey=YOUR_KEY
```

or:

```http
Cookie: API-Key=YOUR_KEY
```

The exact location depends on the API. 

### API keys are secrets

They can leak through:

```text
Source code
Git repositories
Configuration files
Logs
URLs
Screenshots
Unencrypted traffic
Phishing
```

So:

> **Treat API keys as secrets unless the provider explicitly says otherwise.**

# 31. JWT

JWT means:

> **JSON Web Token**

A typical flow:

```text
Client
  ↓
Username + Password
  ↓
API Server
  ↓
Credentials verified
  ↓
JWT generated
  ↓
JWT returned
  ↓
Client stores token
  ↓
Future requests use JWT
```

Example:

```http
Authorization: Bearer <JWT>
```

---

# 32. JWT Structure

A JWT normally looks like:

```text
xxxxx.yyyyy.zzzzz
```

It has three parts:

```text
HEADER.PAYLOAD.SIGNATURE
```

Think:

```text
┌─────────────────────┐
│       HEADER        │
│   Token metadata    │
├─────────────────────┤
│      PAYLOAD        │
│      Claims         │
├─────────────────────┤
│     SIGNATURE       │
│ Integrity check     │
└─────────────────────┘
```

---

# 33. JWT Header

Example:

```json
{
  "alg": "HS512",
  "typ": "JWT"
}
```

Meaning:

```text
alg
 ↓
Signing algorithm

typ
 ↓
Token type
```

---

# 34. JWT Payload

The payload contains **claims**.

Example:

```json
{
  "sub": "1234567890",
  "name": "user1",
  "iat": 1516239022
}
```

Claims can include:

```text
User ID
Username
Issuer
Expiration
Issued-at time
Roles
Permissions
```

Important:

> **JWT payloads are normally encoded, not encrypted.**

Therefore, sensitive secrets should not simply be placed inside a JWT payload. 

---

# 35. JWT Signature

The signature helps the server determine whether the token was properly signed and whether its contents have been modified.

Conceptually:

```text
Header
   +
Payload
   +
Secret / Private Key
   ↓
Signature
```

The server verifies the signature before trusting the token.

---

# 36. JWT Security

JWT itself isn't automatically insecure.

Security depends heavily on the implementation.

Important areas include:

```text
Signing secrets
Algorithm validation
Signature verification
Expiration handling
Token storage
Sensitive payload data
Authorization checks
```

The important mental model is:

```text
HEADER
 ↓
How token is represented/signed

PAYLOAD
 ↓
Claims/data

SIGNATURE
 ↓
Integrity/authenticity verification
```

---

# 37. HMAC

HMAC means:

> **Hash-based Message Authentication Code**

The basic concept is:

```text
Request Data + Secret
          ↓
        HMAC
          ↓
       Signature
          ↓
      API Request
```

The server possesses the same secret.

When the request arrives:

```text
Request Data + Server Secret
          ↓
        HMAC
          ↓
    Calculated Signature
```

The server compares the result.

```text
Same?
 ├── YES → Accept
 └── NO  → Reject
```

HMAC therefore provides a mechanism for verifying **request integrity and authenticity**.

# 38. OAuth 2.0

OAuth 2.0 is commonly misunderstood.

The easy definition is:

> **OAuth allows an application to access resources on behalf of a user without requiring the application to receive the user's password.**

Example:

```text
You
 ↓
Authorization Server
 ↓
Grant permission
 ↓
Access Token
 ↓
Third-Party Application
 ↓
API
 ↓
Allowed Resources
```

The application receives a token rather than the user's password.

The token can be:

```text
Limited
Time-limited
Scoped
Revocable
```



---

# 39. OAuth vs JWT

This is extremely important:

```text
OAuth 2.0
    ↓
Authorization framework

JWT
    ↓
Token format
```

They are **not the same thing**.

An OAuth system can use JWTs, but:

```text
OAuth ≠ JWT
```

The source explicitly emphasizes this distinction.

# 40. No Authentication

Not every API requires authentication.

For example, a public weather API might allow:

```http
GET /api/weather/london
```

without requiring a login.

Examples of potentially public data:

```text
Weather data
Public documentation
Exchange rates
Public datasets
Public information
```

However:

```text
Public API
   ≠
Unlimited API
```

A public API can still use:

```text
Rate limiting
Request restrictions
Other controls
```



---

# 41. Business Logic

After authentication and authorization, the API processes the application's **business logic**.

Business logic means:

> **The rules that determine what the application is supposed to do.**

Example banking rules:

```text
User can view their own account
User cannot transfer more than allowed
Only administrators can delete accounts
A coupon can only be used once
```

The API server enforces these rules. 

Think:

```text
Authentication
      ↓
"Who are you?"

Authorization
      ↓
"What are you allowed to access?"

Business Logic
      ↓
"What is the application supposed to allow?"
```

These are different concepts.

# 42. Database

The API server usually communicates with a database.

Example:

```text
API Server
    ↓
"Find User 1"
    ↓
Database
    ↓
User 1's data
```

The database might contain:

```text
Users
Orders
Payments
Profiles
Settings
Products
Transactions
```

Example:

```text
Users

ID    Username    Email
1     user1       user1@example.com
2     user2       user2@example.com
```

The client normally **does not directly communicate with the database**.

Instead:

```text
Client
  ↓
API Server
  ↓
Database
```

This allows the API to enforce access controls. 

---

# 43. Database Response

The database returns information to the API server.

For example:

```text
Database
    ↓
{
    id: 1,
    username: "user1",
    email: "user1@example.com"
}
    ↓
API Server
```

The API server then decides what information should be returned to the client. 

This is important:

```text
Database Data
      ↓
API Server
      ↓
Filtered / processed response
      ↓
Client
```

The database should not simply dump everything directly to the client.

# 44. HTTP Response

Finally, the API sends an HTTP response.

Example:

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

Body:

```json
{
  "id": 1,
  "username": "user1",
  "email": "user1@example.com"
}
```

The browser/application receives this response and uses it to display or process the information.

# 50. Microservices

A backend doesn't always consist of one huge application.

It can be divided into smaller services.

Example:

```text
                 API Gateway
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
 User Service    Order Service   Payment Service
       │              │              │
       ▼              ▼              ▼
    Database       Database       Database
```

A microservice is a backend service responsible for a particular function.

For an online store:

```text

 ↓
Accounts / Profiles

 ↓
Orders

Payment Service
 ↓
Payments

Email Service
 ↓
Notifications
```

# 51. Monolithic vs Microservices

## Monolithic

Everything exists inside one application:

```text
┌─────────────────────────────┐
│       ONE APPLICATION       │
│                             │
│ Users                       │
│ Payments                    │
│ Orders                      │
│ Emails                      │
└─────────────────────────────┘
```

## Microservices

Different functions are separated:

```text
Users ────────→ User Service

Payments ─────→ Payment Service

Orders ───────→ Order Service

Emails ───────→ Email Service
```

The API consumer usually doesn't need to know which architecture is being used.

# 54. BOLA / IDOR Concept

Suppose you are authenticated as:

```text
User 100
```

You request:

```http
GET /api/users/100
```

and receive your own information.

Now consider another object:

```http
GET /api/users/101
```

The important security question is:

> Is User 100 actually authorized to access User 101?

If the API returns User 101's private information without proper authorization, this can indicate:

```text
BOLA
Broken Object Level Authorization

also commonly called:

IDOR
Insecure Direct Object Reference
```

The key idea:

```text
Authentication
      ↓
"You are User 100."

Authorization
      ↓
"Are you allowed to access User 101?"
```

These are separate checks.

# 57. Authentication Methods — Quick Comparison

# 58. Encoding vs Encryption

This is another important distinction.

### Encoding

Changes how information is represented.

Examples:

```text
URL Encoding
HTML Encoding
Unicode
Base64
```

### Encryption

Protects information so unauthorized parties cannot understand it without the required key.

Remember:

```text
Base64 ≠ Encryption
```

Base64 can be decoded.

The provided API material explicitly emphasizes this distinction.

# 59. JWT vs OAuth vs Authentication

Don't mix these concepts.

```text
Authentication
      ↓
Process of verifying identity

Authorization
      ↓
Process of determining permissions

JWT
      ↓
Token format

OAuth 2.0
      ↓
Authorization framework

HTTPS/TLS
      ↓
Protects communication
```

Very important:

```text
JWT ≠ Encryption
OAuth ≠ JWT
Authentication ≠ Authorization
Base64 ≠ Encryption
```

This distinction is also explicitly summarized in the provided authentication material.
